# 人能用，AI 也能用

> **下一代应用的分水岭，不是"有没有开放 API"，而是 Agent 能不能不靠人转述，直接把事办了。**
>
> 这篇文章给出四条可证伪的判据，并用三个已经出现的样本说明：
> 这个形状不是我们发明的 —— 是它们各自走到的。

---

## 一 · 今天的默认假设：使用者是人

几乎所有软件的交互层，都是按"一个坐在屏幕前的人"设计的：

| 现状 | 对 Agent 意味着什么 |
|---|---|
| 接口面向工程师：鉴权、拼参数、读文档 | 每一步都要人先翻译一次；错一次就断 |
| 输出面向人眼：表格、排版、口语化提示 | Agent 要解析一堆装饰；token 花在去噪上 |
| "AI 功能"是App里的一个客服入口 | AI 是**被使用的东西**，不是**使用者** |
| 能力锁在入口后面 | 人不在电脑前，能力就到不了 |

这里有一个被忽略的事实：**"AI 能用"和"人能用"不是同一套要求。**

人需要排版、引导、容错；Agent 需要**结构化输出、可预演、可自省、可归责**。
给同一份能力做两套交付，往往比做一套通用交付更贵 —— 而这正是现在大多数应用的状态。

---

## 二 · 已经发生的三件事

企业微信、钉钉、飞书 —— 三家互不相干的产品，在同一段时间里长成了**同一个形状**：
把自家工作区能力做成一个**面向 Agent 的命令行工具**，并附上说明书。

| | 交付物 | 给 Agent 的东西 |
|---|---|---|
| 企业微信 | `wecom-cli` | 15 个服务 + 运行时 `schema` 自省 |
| 钉钉 | `dws` | 工作区命令 + `--dry-run` + `--jq` + `dingtalk-*` Skills |
| 飞书 | `lark-cli` | 三层命令粒度 + JSON 契约 + `lark-*` Skills |

**它们的共同点，不是"都有一个 CLI"。** 是这五条：

| | 结构化输出 | 可预演 | 可自省 | Skills | 执行身份 |
|---|---|---|---|---|---|
| 企业微信 | ✅ | 未核实 | ✅ `schema list` | 官方技能包 | 用户本人 |
| 钉钉 | ✅ JSON | ✅ `--dry-run` | ✅ `schema --compact` | ✅ | 用户 OAuth |
| 飞书 | ✅ JSON 契约 | ✅ `--dry-run` | ✅ schema 自省 | ✅ | 用户 OAuth / bot |

这三家**不是照着同一份标准做的** —— 但都收敛到了同一个形状。
这本身就是证据：**当 Agent 真的要来用你的应用时，你只能长成这样。**

## 三 · 四条判据

要判断一个 APP 是不是"Agent 原生"，看这四条。每条都给了反例 —— **反例里发生的事，都是真实会发生的。**

### 🧭 J1 · 可发现：Agent 能自己找到"这件事用哪条命令"

- **正例**：`<cli> schema "<path>" --compact` 直接给出参数、约束、风险语义。
- **反例**：只有一份三年前的 HTML 文档。Agent 要么猜，要么重试到超时。

### 🎬 J2 · 可预演：动手之前能看一眼"会发生什么"

- **正例**：`--dry-run` 展示调用参数但不执行。
- **反例**：先写后看。写错了才发现，而写入已经不可撤销。

### 🪪 J3 · 可归责：以谁的名义执行，可查、可撤销

- **正例**：`auth status` 报当前身份与已授权范围；`auth logout` 能撤销。
- **反例**：一个长期不过期的 token，谁都不知道它代表谁、还剩多少权限。

### 🛑 J4 · 可拦截：人能在它跑起来之前看见并拦下

- **正例**：危险操作有确认；Agent 模式下也可以由外层闸门代管确认。
- **反例**：一个 `--yes` 就跳过所有确认 —— 这时候**外层必须有一道闸**，
  否则"AI 帮你做事"和"AI 替你签字"就没有区别了。

> ⚠️ **J4 是这四条里最容易被跳过的一条**，也是最容易出事的一条。
> 一个能读能写、又不需要确认的 CLI，等于把你的账号交给了一个随时可能被提示注入的模型。
> **可拦截不是"功能"，是入场券。**

## 四 · 多端互通：从 A 进，到 B 出

当"入口"和"执行面"解耦之后，会多出一件事：

```text
在企微里说一句话
  → Agent 判断该用哪只手
  → 到钉钉查待办、到飞书改文档、在本机改代码、到板子上放首歌
  → 结果回到企微同一个气泡
```

这不是"跨平台同步"，也不是"把一个平台的消息转发到另一个"。
**是同一个 Agent 拥有多只手**，它按任务自己选，人只负责说"做什么"和"允不允许"。

要做成这件事，只需要三样东西，而且三样都不是新发明的：

| 需要 | 为什么 |
|---|---|
| **身份边界** | 执行身份可能是"你本人"而不是机器人 —— 必须让人看得见 |
| **审批闸门** | 写操作一律确认；策略表外按写处理（fail-closed） |
| **可替换** | 内核不认识任何具体平台 —— 换一只"手"不改核心 |

---

## 五 · 这不要求平台"全开放"

有一种担心是合理的：**"让 Agent 用我的应用，是不是等于把数据全交出去？"**

不是。我们主张的从来不是"开放一切"，而是：

> **把"已经授权给这个人的能力"，以 Agent 能用的形状暴露出来。**

- 授权范围仍然由**用户和组织**决定（scopes、应用权限、管理员开关）；
- 每一次调用仍然走**平台自己的鉴权与审计链路**，管理员可追溯；
- 撤销仍然是**一个动作**（登出、回收应用、关掉 CLI 访问）。

Agent 拿到的不是"更多权限"，是**同一份权限的另一种使用方式**。

## 六 · 我们做到哪一步

| | 状态 |
|---|---|
| 入口（人与 Agent 说话的地方） | ✅ 企业微信 / 飞书 / Slack，均已真机验收 |
| 执行面 · 本机 | ✅ Bash / 文件 |
| 执行面 · 物理设备 | ✅ MQTT 双向 TLS，六个动词 |
| 执行面 · 钉钉 / 飞书工作区 | ⏳ 待实测（官方 CLI 已就位，接入中） |
| 命令级审批白名单 | ⏳ 未做 —— 当前跨平台**全部弹卡** |

**没打勾之前不写"支持"。** 这四条判据同样适用于我们自己。

---

## 七 · 一句话

> **APP 不只是给人用的界面，也可以是 Agent 的一只手。**
>
> 而一只"手"要被信任，先得能被看见、能被拦下、能被收回。
